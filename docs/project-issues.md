# PaperAssistant：问题与解决方案

本文记录原型在真实运行中发现的问题及其解决方案，用于开发跟踪和项目答辩。每一项都以可验证的验收标准收尾；没有日志或代码依据的内容只作为待验证假设处理。

最后更新：2026-09-18。

## P-01：结构化输出有时不符合 schema

### 问题阐述

MiniMax 在 `ToolStrategy` 下可以产生正确的结构化工具调用，但不保证每次都合规。实际运行中，`classify_query` 曾连续两次违反 `QueryIntent` 的跨字段规则后才成功；`assess_coverage` 曾返回普通响应而没有 `CoverageAssessment` 工具调用。

这意味着 LangChain 的结构化输出能**解析和校验**结果，但不能让底层模型必然生成正确的工具调用。

### 根因

当前使用的是工具型结构化输出：Pydantic schema 被转换成工具定义，模型仍需主动遵循工具调用协议。模型输出是否调用工具、字段是否合法，仍受模型供应商能力影响。

### 解决方法

1. 新增 opt-in live 基准，分别对 `QueryIntent`、`CoverageAssessment`、`ArxivSearchPlan` 和 `GroundedReportDraft` 统计工具调用率、Pydantic 通过率、平均调用次数和延迟。
2. 根据基准结果决定关键结构化节点继续使用 tool calling、切换供应商原生 JSON Schema，或使用 JSON mode 加 Pydantic parser。
3. 无论协议如何，保留 Pydantic 校验；结构化输出不合规时不能直接信任或继续执行有副作用的操作。

### 验收标准

- live 基准可独立运行，不进入默认 CI；
- 每类 schema 都能输出成功率和失败原因分布；
- 关键节点对无工具调用、未知字段、跨字段冲突均能返回明确错误，而不是产生未校验状态。

## P-02：多层重试使用户感觉节点“卡住”

### 问题阐述

当模型不满足结构化约束时，用户此前只能看到工作流停在一个节点；实际可能已经发生多次 LLM 调用，带来不可预期的时间和费用。

### 根因

`ToolStrategy(handle_errors=True)` 会请求 Agent 修复结构化错误；外层 Agent retry 和模型客户端传输重试又可能叠加，形成多个重试层级。

### 解决方法

1. 每个节点定义单一、有限的重试预算，例如“首次调用 + 一次结构化修复”。
2. 明确区分并记录三类重试：网络、结构化解析、业务校验；禁止外层重跑整个 Agent 来掩盖内部结构化失败。
3. 保留手工 runner 的 LLM 开始、结束、结构化结果日志；在失败时输出节点名、调用次数和最后一个错误原因。
4. 达到预算后，转入可读的失败/降级状态，而不是无限等待或 traceback。

### 验收标准

- 任意结构化节点的最大模型调用次数可从配置确定；
- 人工运行能看到每次 LLM 调用及其结果；
- 结构化失败在有限时间内终止并给出可读状态。

## P-03：论文“直接导入”和“检索后导入”意图混淆

### 问题阐述

用户说“找一篇论文，导入后介绍核心方法”时，模型容易选择 `paper_import`；但用户尚未提供 arXiv ID、DOI 或 URL，当前 `QueryIntent` 又规定 `paper_import` 必须使用 `direct_import`。模型因而需要多次修复才能路由正确。

### 根因

自然语言的“导入”涵盖两件事：导入用户已经指定的论文，或检索候选后经人工选择再导入。当前 schema 将两者混为一个任务类型。

### 解决方法

1. 明确以下语义：
   - `direct_import`：用户已经给出 arXiv ID、DOI 或 URL；
   - `literature_discovery`：先检索候选，人工选择后导入；
   - `paper_import` 仅表示前者，或替换为更明确的 `direct_paper_import`。
2. 在分类 prompt 和 fixture 中加入正反例，明确“找一篇并导入”必须走 `literature_discovery`。
3. schema validator 保持严格：没有论文标识时禁止直接下载。

### 验收标准

- “请找一篇 X 论文，导入后介绍”一次分类为检索路径；
- “导入 arXiv:xxxx.xxxxx”一次分类为直接导入路径；
- 两类请求均不依赖结构化重试来获得正确路由。

## P-04：arXiv 查询扩展过宽，导致候选主题漂移

### 问题阐述

针对 “Diffusion Models for Recommendation”，实际搜索计划既有 `diffusion model recommendation`，也有宽泛的 `generative recommendation`。查询编译器用 OR 连接这些短语，结果召回大量不含 diffusion 的生成式推荐论文。

### 根因

搜索计划没有区分“必须命中的核心概念”和“可选扩展概念”；确定性查询编译器又允许任一扩展词独立召回结果。

### 解决方法

1. 将 `ArxivSearchPlan` 设计为 `required_terms` 与 `optional_expansions`；核心术语采用 AND 约束。
2. 编译器只用核心术语构造基础查询；扩展词只用于候选排序，不能绕过核心约束。
3. 在本地对标题和摘要执行确定性术语覆盖过滤。例如请求含 `diffusion` 时，默认剔除标题和摘要均不含 `diffusion` 的候选。
4. 按核心词命中、标题命中、摘要命中、类别匹配等可解释信号排序，默认仅展示少量高相关候选。

### 验收标准

- “Diffusion Models for Recommendation” 的默认候选全部至少命中 `diffusion` 和 `recommendation` 的核心约束；
- 候选列表提供命中理由；
- 离线测试能阻止仅含 `generative recommendation` 的无关结果排在前列。

## P-05：导入后回答未绑定到本次选择的论文

### 问题阐述

一次“导入后介绍核心方法”的报告校验错误指向既有本地 FlowCF chunk，而不是本次导入论文。这说明增强检索可以从整个库中取旧证据，存在用旧论文回答新导入论文的风险。

### 根因

`retrieve_augmented_library` 只做全库检索，没有把“用户要求介绍本次导入论文”表达为可执行的来源范围约束。

### 解决方法

1. 在状态中保存 `selected_paper_ids`，并向增强检索和报告上下文传入 `source_scope`。
2. 对“介绍/分析本次导入论文”类任务，报告 claim 的 `evidence_id` 必须属于 `selected_paper_ids`。
3. 如果已导入论文没有足够可用文本，返回“导入成功但证据不足”，不能回退到旧库拼凑回答。

### 验收标准

- 指定导入论文的报告引用只来自本次选中的论文；
- 导入论文解析失败或检索不到证据时，系统明确说明，而不使用其他论文替代；
- 集成测试能验证来源范围约束。

## P-06：引用逐字校验失败会让 CLI 崩溃

### 问题阐述

报告 Agent 可以返回合法的 `GroundedReportDraft`，但其中 `supporting_quote` 可能不是对应 excerpt 的连续原文。当前逐字校验正确地抛出 `ValueError`，但异常未被工作流处理，导致 CLI traceback 退出。

### 根因

结构化 schema 只保证字段形状，不能保证 `supporting_quote` 与数据库证据之间的逐字语义约束；节点将这个可预期的校验失败作为未处理程序异常。

### 解决方法

1. 继续采用确定性的逐字引用校验，不能因模型失败而放宽此规则。
2. 将失败的 claim、evidence ID 与校验原因构造成修复上下文，只允许报告 Agent 修复一次。
3. 第二次仍失败时，写入 `report_grounding_failed` 状态和用户可读说明，不渲染未经验证的报告，也不抛 traceback。
4. CLI/API 层将该状态正常展示，并保留可诊断日志。

### 验收标准

- 伪造、拼接或改写的 quote 一律不能出现在最终报告；
- 首次校验失败可以进行一次受控修复；
- 连续失败后工作流以明确状态结束，命令行退出码和输出均可预期。

## P-07：人工审批候选列表缺少质量控制

### 问题阐述

当前审批阶段可能展示十几篇候选，且没有主题命中或排序理由。用户在候选质量较差时容易误选多篇无关论文并把它们永久写入本地知识库。

### 根因

候选列表直接暴露原始 arXiv 召回结果，尚未经过核心词过滤、重排序和有限数量控制。

### 解决方法

1. 先实施 P-04 的检索过滤与排序。
2. 将默认展示数量限制为高相关候选，例如 5 篇；允许用户显式扩展查看其余结果。
3. 在每项候选中展示标题、摘要、类别、核心词命中和简短相关性理由。
4. 导入前再次显示将要写入的论文 ID 与标题，防止误选。

### 验收标准

- 审批默认只展示经过相关性过滤和排序的少量候选；
- 每个候选均有可解释的匹配信息；
- 无关论文不能在没有用户明确扩展/选择的情况下进入导入队列。

## P-08：通用知识问题被错误送入论文检索与导入链路

### 问题阐述

用户提问“介绍一下生成模型”时，没有要求论文、引用或外部检索，工作流仍执行了本地 RAG、覆盖度评估、arXiv 搜索和论文导入审批。虽然覆盖度评估正确指出本地“生成式推荐”论文不足以介绍 GAN、VAE 和扩散模型，但这条产品路径不符合通用知识问答的需求。

### 根因

当前图中缺少 `general_explanation` 路由。分类后，非澄清/非越界的请求默认进入 research 路径；覆盖度不足只能请求 arXiv 搜索，不能选择基于模型已有知识的通用说明。

### 解决方法

1. 在 `QueryIntent` 中区分 `general_explanation` 与需要文献证据的研究型问题。
2. 为 `general_explanation` 增加独立终端节点：使用对话模型回答基础概念，并清楚标注回答不基于本地论文证据。
3. 仅当用户明确要求论文、引用、文献检索/导入，或通用回答后主动要求扩展资料时，才进入 arXiv 支线。
4. 保留“本地资料不足”的判断，但让它只影响研究型问题，不将一般问答强制升级为导入任务。

### 验收标准

- “介绍一下生成模型”“什么是推荐系统”等通用问题不触发 arXiv 审批；
- “找论文介绍生成模型”“给出生成模型相关论文和引用”等请求进入文献路径；
- 通用回答与基于本地论文的回答在状态和输出中可区分。

## P-09：PDF 布局解析误判，单篇失败中止整批导入

### 问题阐述

批量导入四篇论文时，第一篇 `arxiv:2002.02112` 成功入库；第二篇 `arxiv:1708.07012` 下载成功但解析失败，导致整批工作流 traceback 退出，后两篇没有执行。

失败论文并非扫描件或空文件：它有 9 页，PyMuPDF 可抽取约 2504 个词。当前 layout parser 过滤正文后，最大保留块只有 58 token，低于 120 token 最小 chunk 阈值，因此抛出 “OCR may be required”。这条提示对该文件不准确，真实问题是版面过滤/分块策略丢失了可抽取正文。

### 根因

1. 解析器只有 layout-aware 一种策略；没有 chunk 时直接归因为 OCR 问题，未检查原始页文本是否仍然充足。
2. `ingest_papers` 顺序导入并直接传播单篇异常，没有收集逐篇结果或定义部分成功状态。

### 解决方法

1. 保留 layout-aware parser 作为首选策略；若其没有生成 chunk、但原始 `page.get_text("text")` 具有足够文本，则回退到保守的原始页文本分块策略。
2. 仅在原始文本也不足时提示 OCR；错误信息应区分“扫描/无文本”“布局解析丢失正文”“分块阈值不足”。
3. 不全局降低 `min_chunk_tokens`，避免页眉、页脚、图注和碎片噪声污染 Chroma。
4. 为批量导入定义逐篇成功/失败 outcome。至少一篇成功时，只以成功论文继续增强检索；全部失败时进入 `ingestion_failed` 终端状态。
5. CLI/API 正常展示每篇论文的结果、失败原因和可重试项，不暴露 Python traceback。

### 验收标准

- 有足够可抽取文本但 layout parser 失败的 PDF 能通过 fallback 产生可追溯 chunk；
- 真正扫描/无文本 PDF 才报告需要 OCR；
- 一篇导入失败不会阻止其他已批准论文继续处理；
- 部分成功、全部失败和重试场景均有离线测试，且最终报告只使用成功入库的论文。

## 实施顺序

1. P-03、P-08：先消除意图和路由的语义冲突。
2. P-04、P-07：保证检索候选相关，避免污染知识库。
3. P-09：修复解析 fallback 和批量导入部分失败处理。
4. P-05：保证“导入后回答”只用正确来源。
5. P-06：把安全校验失败变为受控工作流结果。
6. P-01、P-02：用 live 基准选择结构化协议，并收紧重试预算。
7. 将以上每项的验收标准固化为离线 unit/integration 测试；真实模型测试仍保持 opt-in。

## 可用于答辩的总结

> 系统已打通本地 RAG、人工审批、arXiv 检索、论文入库、向量化和证据报告的主链路。当前改进重点不是放宽模型约束来获得“看起来能跑”的结果，而是通过意图 schema、核心术语检索、来源范围、逐字引用校验和有限重试，让每个模型输出都能被验证、解释和安全地失败。
